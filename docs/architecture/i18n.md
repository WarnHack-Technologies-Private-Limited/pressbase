# Internationalisation

Pressbase can run in another language, with WordPress's own translations where they exist. The server translates with a port of WordPress's `l10n.php`; the admin and the block editor translate with `@wordpress/i18n`, as WordPress's scripts do. The decision is in [ADR 0015](../adr/0015-internationalisation.md); translators start with [Translating Pressbase](../development/translating.md).

| Piece | Location | WordPress equivalent |
|---|---|---|
| Reading `.mo`, `.po`, JSON | `apps/core/src/i18n/translation-file.ts` | `WP_Translation_File_MO`, `PO`, `load_script_translations()` |
| Plural forms | `apps/core/src/i18n/plural-forms.ts` | `Plural_Forms` (`wp-includes/pomo/plural-forms.php`) |
| Loaded translations | `apps/core/src/i18n/controller.ts` | `WP_Translation_Controller` |
| `kernel.i18n` | `apps/core/src/i18n/l10n.ts` | `wp-includes/l10n.php`, `WP_Textdomain_Registry`, `is_rtl()` |
| Month and weekday names | `apps/core/src/i18n/locale.ts`, `blocks/php-date.ts` | `WP_Locale`, `wp_date()` |
| Language packs | `apps/core/src/i18n/language-packs.ts` | `wp-admin/includes/translation-install.php`, `Language_Pack_Upgrader` |
| REST | `apps/core/src/routes/languages.ts` | (none: WordPress's screens call PHP) |
| Plugins | `apps/core/src/plugins/i18n.ts` (`api.i18n`) | `load_plugin_textdomain()` |
| Admin | `apps/admin/src/lib/i18n/` | `wp_set_script_translations()`, `wp.i18n` |
| Templates | `apps/core/src/i18n/extract.ts` → `languages/*.pot` | `wp i18n make-pot` |

## Text domains

A text domain is a set of strings with their own translations.

| Domain | Strings | Translations, in lookup order |
|---|---|---|
| `default` | WordPress's own (block markup, dates, the editor) | `<dataDir>/languages/{locale}.mo`, then `admin-{locale}.mo` |
| `pressbase` | Pressbase's server strings (REST errors…) | `languages/pressbase/pressbase-{locale}.mo`, then the repository's `languages/`; then the `default` domain |
| `pressbase-admin` | Pressbase's admin | the same places, `pressbase-admin-{locale}`; then the `default` domain |
| a theme's (`twentytwentyfive`) | its patterns | `languages/themes/{domain}-{locale}.mo`, then the theme's `languages/` |
| a plugin's (its slug) | `api.i18n` | `languages/plugins/{domain}-{locale}.mo`, then the plugin's `languages/` |

Every place takes a `.po` with the same name when there is no `.mo` (Pressbase reads `.po` files directly; WordPress needs them compiled). Fuzzy and untranslated entries are skipped, as `msgfmt` skips them. When several files serve a domain, the first that has a string wins (`WP_Translation_Controller::locate_translation()`).

**Borrowing WordPress's translations.** A string missing from a Pressbase domain is looked up, unchanged, in WordPress's `default` domain. Many of Pressbase's strings are WordPress's ("Posts", "Settings", the month names), so installing WordPress's German pack translates much of Pressbase's admin before anyone translates Pressbase. For the admin, core sends only the strings in `languages/pressbase-admin.pot`, and decodes HTML entities in borrowed strings (WordPress's PHP strings are often printed as HTML: `&rsaquo;`). The trade-off: Pressbase writes in sentence case ("Visit site"), WordPress in title case ("Visit Site"), so only identical strings are borrowed.

## Translating on the server

```ts
kernel.i18n.__('Posts');                                    // default domain
kernel.i18n._x('Read', 'verb', 'my-plugin');
kernel.i18n._n('%s comment', '%s comments', count, 'pressbase');
kernel.i18n._nx('%s file', '%s files', count, 'upload', 'pressbase');
kernel.i18n.esc_html__('Skip to content');                 // also esc_attr__, esc_html_x, esc_attr_x
kernel.i18n.translate(text, domain, locale);               // with an explicit locale
```

Translating is **synchronous**, as in WordPress, so it works anywhere (the PHP pattern interpreter, block render callbacks). A domain's files are read the first time it's used in a locale (`_load_textdomain_just_in_time()`), parsed, and kept; a file is parsed again only when it changes on disk. A real WordPress core `.mo` (5,000 strings) parses in about 50 ms.

`loadTextdomain(domain, file, locale)`, `unloadTextdomain(domain, reloadable)`, `loadPluginTextdomain(domain, dir)` and `loadThemeTextdomain(domain, dir)` work as in WordPress. `hasTranslation()`, `isTextdomainLoaded()`, `getAvailableLanguages()`, `getInstalledTranslations(type)` and `isRtl()` are there too.

### Plural forms

A translation's `Plural-Forms` header (`nplurals=3; plural=(n%10==1 && n%100!=11 ? 0 : …)`) is a C expression. `PluralForms` parses it with the shunting-yard algorithm and evaluates it on a stack, never with `eval`, so a translation file can't run code. An invalid header falls back to English's rule (only 1 is singular), as WordPress does.

## Which language

WordPress decides once per PHP request. Pressbase serves requests in several languages at once, so the language travels with each request in `AsyncLocalStorage`:

- **The site's language** is the `locale` option (WordPress's `WPLANG`), exposed as `language` in `/wp/v2/settings` and chosen in Settings → General. Only `en_US` and installed languages are accepted. `kernel.i18n.getLocale()` reads it (filter `locale`).
- **A user's language** is their `locale` user meta (Profile → Language). `''` means the site's. `/wp/v2/users/me?context=edit` returns `locale` (the effective language, `get_user_locale()`) and Pressbase's `locale_setting` (the stored choice).
- **A request's language** (`determine_locale()`) is set by the `requestLocale` middleware for every REST request: the user's when the request asks with `?_locale=user` (the block editor's api-fetch adds it, as in WordPress, and so does the admin), `?wp_lang=` on the login screen, the site's otherwise. Filters: `pre_determine_locale`, `determine_locale`.
- **Public pages** are always in the site's language, as in WordPress. Changing it purges the page cache (every `updated_option` does) and reloads the active theme, whose patterns are translated when they register.

`kernel.i18n.withLocale(locale, fn)` runs code in another language (WordPress's `switch_to_locale()`).

### Right to left

`isRtl(locale)` reads the translation of `ltr` (context `text direction`), as `WP_Locale` does; without one, a list of right-to-left languages answers (`ar`, `he`, `fa`, `ur`…). Then:

- the public site prints `<html dir="rtl" lang="…">`, adds the `rtl` body class and serves `style-rtl.min.css` for the block library;
- the admin sets `dir="rtl"` on `<html>`, and the block editor loads the `-rtl` copies of WordPress's stylesheets and gets `isRTL: true`.

The admin's own CSS mostly uses flex and grid, so it mirrors; some spacing still uses physical properties (`margin-left`…) and needs a pass with logical properties.

### Dates

`formatPhpDate(format, date, timeZone, words)` takes `WP_Locale`'s words: `F`, `M`, `l`, `D`, `a` and `A` print the month and weekday names, abbreviations and am/pm in the language being rendered (`kernel.i18n.dateWords()`, translated through the `default` domain with WordPress's exact strings and contexts, e.g. `_x('Oct', 'October abbreviation')`). Block render callbacks get them through `siteInfo()` (`theDate()`, the archives block). Not yet: `wp_maybe_decline_date()`'s genitive month names, and localised digits.

| `ngettext`, `ngettext_{domain}` | filter | `translation, single, plural, number, domain` | every `_n()` |
| `ngettext_with_context`, `ngettext_with_context_{domain}` | filter | `translation, single, plural, number, context, domain` | every `_nx()` |
| `locale` | filter | `locale` | `getLocale()` |
| `pre_determine_locale`, `determine_locale` | filter | `locale` | a request's language |
| `override_load_textdomain`, `pre_load_textdomain` | filter | `override, domain, mofile, locale` | short-circuit `loadTextdomain()` |
| `load_textdomain` | action | `domain, mofile` | before a file loads |
| `load_textdomain_mofile`, `load_translation_file` | filter | `mofile, domain` / `file, domain, locale` | the file to load |
| `override_unload_textdomain` / `unload_textdomain` | filter / action | `override, domain, reloadable` / `domain, reloadable` | `unloadTextdomain()` |
| `get_available_languages` | filter | `languages, dir` | installed languages |
| `pre_load_script_translations`, `load_script_translation_file`, `load_script_translations` | filter | as WordPress | each JSON file for the block editor |
| `translations_api`, `translations_api_result` | filter | `result, type, args` | WordPress.org's translations API |

Translation filters run **synchronously** (`applyFiltersSync`): an `async` callback is skipped with a warning, because translating can't wait.

## Languages and language packs

Installed languages live in `<dataDir>/languages/`, WordPress's `wp-content/languages/` layout:

```
languages/
  de_DE.mo  de_DE.po                       WordPress core (default domain)
  admin-de_DE.mo  admin-de_DE.po           WordPress admin strings (default domain)
  de_DE-{md5}.json                         script translations (the block editor)
  themes/twentytwentyfive-de_DE.mo         a theme's
  plugins/{plugin}-de_DE.mo                a plugin's
  pressbase/pressbase-admin-de_DE.po       Pressbase's own, overriding the bundled ones
```

The repository's `languages/` folder holds Pressbase's templates (`pressbase.pot`, `pressbase-admin.pot`) and contributed translations (`pressbase-admin-de_DE.po`…), which ship with Pressbase.

`getAvailableLanguages()` lists locales with a core file (`de_DE.mo` or `.po`, not `admin-`, `continents-cities-`…) or a Pressbase admin translation. Their names come from WordPress.org's list when it was fetched, else from the runtime's ICU data (`Intl.DisplayNames`), so they work offline.

**Installing a language** is an explicit action in Settings → General ("Add a language…"), for users with `install_languages` (granted with `update_core`, `install_plugins` or `install_themes`, as `wp_maybe_grant_install_languages_cap()` does):

1. `GET /pressbase/v1/languages/available` asks `https://api.wordpress.org/translations/core/1.0/?version=7.1.3` (`translations_api()`), cached for three hours in the `_site_transient_available_translations` option.
2. `POST /pressbase/v1/languages` `{ "language": "de_DE" }` downloads the core pack (`wp_download_language_pack()`), then asks the themes API for each installed theme (`/translations/themes/1.0/?slug=twentytwentyfive&version=1.5`) and installs the language's pack into `languages/themes/`.

Downloads come only from `https://downloads.wordpress.org` (50 MB at most), go through the strict zip reader plugins use (`files/zip.ts`), and only flat `.mo`, `.po` and `.json` files are written, each through a temporary file and a rename. WordPress's `.l10n.php` files are never written: Pressbase doesn't run PHP. The version asked for is `WORDPRESS_TRANSLATIONS_VERSION` in `language-packs.ts`; bump it with the `@wordpress/*` packages. Tests replace `kernel.i18n.packs.fetch`.

## REST

| Route | Who | What |
|---|---|---|
| `GET /pressbase/v1/i18n/admin` | anyone, also before installation | the admin's strings for `@wordpress/i18n`: `{ locale, lang, dir, locale_data: { 'pressbase-admin': … } }`, with an ETag |
| `GET /pressbase/v1/i18n/editor` | anyone (installed) | the block editor's: `{ locale, lang, dir, locale_data: { default: … } }` |
| `GET /pressbase/v1/languages` | signed in (`read`) | `{ site_language, installed: [{ language, english_name, native_name, dir, wordpress }], can_install }` |
| `GET /pressbase/v1/languages/available` | `install_languages` | WordPress.org's packs |
| `POST /pressbase/v1/languages` | `install_languages` | install one; `{ language, core, themes, skipped, installed }` |

Add `?_locale=user` for the user's language.

## The admin

`apps/admin/src/lib/i18n/`:

- **Server components** call `const { __, _x, _n, sprintf } = await getI18n()` (`server.ts`), which fetches `/pressbase/v1/i18n/admin?_locale=user` once per request (React `cache()`).
- **Client components** call `const { __ } = useI18n()` (`context.tsx`). The root layout puts the same data in an `I18nProvider` and sets `<html lang dir>`.
- Each request and the browser get their own `createI18n()` instance, never `@wordpress/i18n`'s shared one: one server renders pages for people in different languages at the same time.
- **Always pass the domain**: `__('Settings', 'pressbase-admin')`. The extractor collects strings by it.
- **Static data** (navigation labels, lists) is marked with `msgid('Posts')` (or `msgid('Oct', 'October abbreviation')`) and translated where it's shown: `__(item.label, 'pressbase-admin')`.
- Put placeholders in the string and fill them with `sprintf`, with a `// translators:` comment saying what they are. Never build a sentence from pieces.
- Saving a new language (Settings → General, Profile) calls `router.refresh()`; the root layout fetches the new language and the provider re-renders.

### The block editor

Gutenberg's packages translate with `@wordpress/i18n`'s shared instance, domain `default`. Before the editor's module loads, `components/block-editor/translations.ts` fetches `/pressbase/v1/i18n/editor?_locale=user` and calls `setLocaleData(data, 'default')`, which is what `wp_set_script_translations()` arranges in WordPress. It must come first: `registerCoreBlocks()` translates block titles as it registers them. Core merges, for the language:

- every script translation in the core pack (`{locale}-{md5}.json`) whose source is one of WordPress's editor scripts (`wp-includes/js/dist/*.js`), into one `default` domain (WordPress loads one file per script handle; Pressbase bundles the packages into one chunk);
- the strings the server translates in WordPress: block metadata (`block title`, `block description`, `block keyword`, style and variation labels) and the text direction, from the core `.mo`.

The editor's toolbar uses WordPress's strings ("Add block", "Undo", "Add title") through the same instance, so the pack translates it too.

## Themes

`themes/php-patterns.ts` interprets `__()`, `_e()`, `_x()`, `esc_html__()`, `esc_html_e()`, `esc_attr__()`, `esc_attr_e()`, `esc_html_x()`, `esc_attr_x()` through the context's `gettext` and `gettextWithContext`, which the theme service binds to `kernel.i18n` in the **site's** language. Pattern titles and descriptions are translated with the contexts `Pattern title` and `Pattern description`, and the theme's pattern category labels through its text domain, as `_register_theme_block_patterns()` does.

Trade-off: WordPress registers patterns on every request, in that request's language; Pressbase registers them once, in the site's language, and again when it changes. A user whose own language differs sees the patterns in the inserter in the site's language.

Not yet: `theme.json` strings (template part titles, preset names: `translate_settings_using_i18n_schema()`), and the theme's `style.css` headers.

## Plugins

A plugin's text domain is its slug. Its `languages/` folder is registered when it loads (`load_plugin_textdomain()`), and forgotten when it's deactivated:

```ts
export default definePlugin((api) => {
  api.i18n.__('Daily tip');                 // domain: the plugin's slug
  api.i18n._x('Post', 'verb');
  api.i18n._n('%d tip', '%d tips', count);
  api.i18n.locale();                         // 'de_DE'
});
```

`my-plugin/languages/my-plugin-de_DE.po` (or `.mo`) is used with no call; `<dataDir>/languages/plugins/my-plugin-de_DE.mo` wins over it. `wp i18n make-pot` can build the plugin's template from `api.i18n.__('…', 'my-plugin')` calls when the domain is written out.

## Templates and contributing

`pnpm i18n:extract` writes `languages/pressbase.pot` and `languages/pressbase-admin.pot` from the source (TypeScript's parser finds the calls; `translators:` comments become notes). A test (`i18n/extract.test.ts`) fails when a template's strings are out of date; moving code doesn't count. See [Translating Pressbase](../development/translating.md).
